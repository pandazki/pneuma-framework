# 回滚:三层,而非一层

Builder 点了 **Rollback**。到底什么回退了?诚实的答案是:一次已部署的变更同时活在
三个地方,而回滚刻意只触碰其中一个。

![回滚立即回退代码、原样保留 additive 数据、把部署留到重新发布](/diagrams/rollback-semantics.png)

## 三层

| 层 | 回滚做什么 | 为什么 |
|---|---|---|
| **代码** | 立即回退——active 版本指针从 `v2 → v1`。 | 上一版本已物化,切回去安全且瞬时。 |
| **数据** | **什么都不做。** additive 的列/表留在数据库里。 | 删掉是不可逆的数据丢失。v1 的代码前向兼容,会忽略它。 |
| **部署** | 重新发布前**什么都不做**。线上 URL 仍服务 v2。 | 部署是显式、需凭证的动作;回滚是一次本地版本决策。 |

## 为什么"只回代码"是安全默认

诱惑在于把回滚做成"撤销一切"。那恰恰是错误的默认,因为三层的可逆性不同:

- **代码可廉价回退。** 版本物化为 `vN` 目录,上一个就在那儿。把 active 指针移回去
  是无损的。
- **数据不行。** 如果 `v2` 加了一个 `environment` 列,而 End User 往里写了值,一次
  "撤销 schema"的回滚会悄悄删掉那些数据。框架拒绝让破坏性数据变更隐式发生。这正是
  [迁移 additive 且 forward-only](/zh/architecture/governed-loop)的初衷——根本没有
  down-migration 可跑。
- **部署是对外效应。** 把线上 URL 重新指向旧构建,是一次带真实凭证、真实回执的真实
  部署。回滚只是 Builder 关于哪个版本*active* 的本地决策;它不会单方面重新部署。

前向兼容正是"保留数据"安全的原因:v1 的 repository 只 select 它认识的列,所以遗留的
`environment` 列是惰性的。我们正是这样验证过的——回滚后,线上 v0 应用正常服务,而
来自 v1 的 `release_checklist_items` 表仍原封不动地躺在数据库里。

## 那要怎么真正回退?

每一层都有显式、受治理的路径——绝不是悄悄的:

1. **回退线上应用** → 重新发布回滚后的版本。发布 `v1` 会从 `v1` 创建一个新部署并
   返回回执;线上 URL 又服务 `v1` 了。
2. **回退 schema/数据**(罕见,且通常不该)→ 编写一个**纠正性 proposal**:一个
   *全新的、向前的*迁移来 drop 那一列,像任何其他变更一样被审查和批准。这是一次
   刻意的、有证据的行为——而非点 Rollback 的隐藏副作用。

规则,只说一次:

> 代码瞬时回退。**数据和部署永不自行回退**——回退它们永远是一次显式、受治理的步骤。

## 这告诉你框架的什么

这就是整个领域模型的形状。一个读作单一动词("rollback")的概念,分解成三层、各有
不同的不变量(可逆 / additive / 对外),各有自己受治理的路径。框架的职责,是让这些
区分无法被意外搞错——这就是为什么"回滚只回代码"是一条不变量,而非一种偏好。
