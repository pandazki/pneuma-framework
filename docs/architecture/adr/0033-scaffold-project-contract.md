# ADR-0033: Scaffold Project Contract For Governed Code-Change Lanes

**Status**: Accepted
**Date**: 2026-05-07
**Deciders**: Pandazki, Codex
**Tags**: `creation-host, scaffold, build-agent, code-change, guardrails`

---

## Context

RC pressure from DevBoard Studio exposed a sharp boundary: the framework can govern semantic `definition.apply` mutations and can persist Builder conversation through BuildThread, but it cannot yet claim that a Build-phase Agent can safely write generated-app source code in a real Host.

The missing piece is not "let opencode edit files." The missing piece is a framework-readable contract that says:

- what a Developer-provided scaffold project contains;
- which generated-app paths are agent-writable;
- which framework integration, lifecycle, publish, and credential paths are protected;
- which checks must pass before the Host asks the Builder to approve;
- which checks must pass before and after applying an approved code change;
- what evidence must be shown with the proposal.

Without that contract, every Host invents its own ad hoc prompt rules, tool allowlists, protected-path checks, and test gates. The result is not portable enough for downstream Developers and not inspectable enough for framework diagnostics.

This ADR complements:

- [ADR-0031](./0031-open-ended-definition-artifact-boundary.md): open-ended UI/module artifacts are Host-owned in v0.
- [ADR-0032](./0032-build-thread-primitive.md): Builder conversation and proposal/decision/receipt turns are framework-visible.
- [ADR-0030](./0030-lifecycle-subsystem-contract.md): lifecycle scripts are a runtime subsystem behind semantic lifecycle verbs.

---

## Decision

Introduce `ScaffoldProjectManifest` as a first-class Creation Host Authoring Kit contract.

The scaffold manifest is Host-owned. The framework validates only generic safety shape:

```text
pneuma.scaffold.json
  -> materialization
  -> artifact boundary
  -> agent contract
  -> guardrails
  -> lifecycle commands
  -> evidence requirements
```

Core exports:

- `ScaffoldProjectManifest`
- `ScaffoldGuardrailCheck`
- `ScaffoldLifecycleCommand`
- `validateScaffoldProjectManifest`

The starter CLI now emits `pneuma.scaffold.json`, and `doctor-host` accepts:

```bash
pneuma-framework doctor-host \
  --workspace ./workspace \
  --profiles ./profiles.json \
  --scaffold-project ./pneuma.scaffold.json
```

## Contract Semantics

### Materialization

The Developer declares where the initial generated-app scaffold comes from and which files never enter drafts.

`source_roots` must be relative workspace paths. Path escapes such as `../outside` are rejected.

### Artifact Boundary

The Developer declares:

- `writable_roots`: the only draft-editable generated-app code paths;
- `protected_paths`: framework integration, lifecycle, publish, and manifest paths the agent must not modify;
- `generated_roots`: code generated by the Host or agent;
- `share_include`: portable source artifacts;
- `share_exclude`: private runtime artifacts, including `.env`.

A protected path cannot live inside a writable root. This intentionally prevents a broad writable root such as `src` from swallowing `src/framework` or release-critical scripts.

### Agent Contract

The manifest supplies prompt material and rules:

- `allowed_tasks`
- `forbidden_tasks`
- `system_prompt_fragments`
- `tool_policy: "draft-workspace-only"`

The first policy is deliberately narrow. Build-phase code writing should happen in a draft workspace, not directly in the published runtime or source-of-truth version.

### Guardrails

The guardrail phases are:

```text
pre_proposal  -> run before asking Builder approval
pre_apply     -> run after approval, before applying/promotion
post_apply    -> run after apply, before receipt/completion
```

The crucial product rule is:

> If pre-proposal checks fail, the Host should not ask the Builder for approval.

A failed typecheck, protected-path check, or diff computation failure is not an approval question. It is a draft failure the Build-phase Agent or Host must resolve or report.

Guardrails can be:

- `kind: "command"`: Host-owned command such as `bun run typecheck`;
- `kind: "framework"`: framework-known checks such as `protected-paths-unchanged`, `base-snapshot-unchanged`, `diff-computable`, or `preview-health`.

### Lifecycle

The scaffold manifest declares the Host's generated-app lifecycle commands for preview, build, test, and optional publish.

These commands remain Host-owned. The framework does not run arbitrary commands from the manifest automatically in this ADR. It validates that the Host has declared a coherent contract, so Code Change Lane helpers can consume it when the Host opts into that lane.

### Evidence

The manifest requires proposal evidence:

- diff;
- guardrail check results;
- changed files;
- optional preview URL.

The evidence requirement ties the code-change lane back to Pneuma's larger governance model: Builder approval should be about one coherent intent with visible impact, not a sequence of unrelated file writes.

## Consequences

### Positive

- Downstream Hosts get a machine-readable place to describe their scaffold and code-editing boundary.
- `doctor-host` can fail fast when a Host would let an agent edit protected framework or release files.
- The Build-phase Agent can receive rules generated from Developer-authored manifest data instead of hand-written prompt drift.
- The approval lane can distinguish draft repair from Builder approval. Failed pre-proposal checks stop before approval.

### Negative / Risks

- This is a contract and diagnostics slice, not a full opencode code-writing runtime.
- M26/MRC 0.1.3 later added the first Code Change Lane executor against this contract: draft workspaces, guardrails, diffs, approval evidence, apply/rollback, and BuildThread receipts. That executor remains a minimal local lane, not a full hosted code-editing product.
- The initial `tool_policy` is intentionally narrow. More policies may be needed for specialized Hosts.

### Follow-ups

- Add a downstream migration guide when a release tag ships this contract.
- Consider richer scaffold-level extension hooks for Developer-owned static analyzers, security checks, and provider-specific Host validation.
- Continue pressure-testing whether Host-owned open-ended artifacts should remain in Code Change Lane / HostExtension slots or deserve a future framework definition-row model.
