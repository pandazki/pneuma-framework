# ADR-0030: lifecycle subsystem contract

**Status**: Accepted
**Date**: 2026-05-04
**Deciders**: Pandazki, Codex
**Tags**: lifecycle, runtime, creation-host, process-management
**Depends on**: [ADR-0029](./0029-supersede-v0-design-spec.md)

---

## Context

ADR-0029 superseded the original lifecycle-script-centric v0 design. The framework's core primitive is now **Operation + definition-as-data**, not "an agent edits files and the framework runs scripts".

That does **not** mean lifecycle disappears. Generated Applications and Published Applications still need to be set up, previewed, stopped, built, migrated, forked, deployed, restarted, and observed. The question is how to keep lifecycle useful without letting it reclaim the top-level model.

M12-M16 also introduced a Reference Creation Host that uses Bun TypeScript and local process management. That raised a boundary question: is lifecycle still a framework contract, or merely example code?

We need a stable answer before release-candidate review.

---

## Options considered

### Option A: restore shell lifecycle as the primary framework model

Reject. This would undo ADR-0029 and make app creation depend on agent-authored file/script mutation again.

### Option B: remove lifecycle from framework core

Reject. Every Creation Host would reinvent process supervision, preview readiness, logs, build artifacts, migration handoff, restart semantics, and agent-facing lifecycle tools.

### Option C: keep lifecycle as a runtime subsystem behind semantic tools

Accept. Lifecycle remains a framework-owned subsystem, but its public surface is semantic tooling and state observation. Shell scripts are one implementation lane, not the primitive.

---

## Decision

1. **Lifecycle is a runtime subsystem.** It is not the framework's top-level primitive and must not replace Operation / definition-as-data in plans, docs, or agent prompts.
2. **Lifecycle is invoked through semantic tools.** Build-phase Agents and Creation Hosts call lifecycle semantics such as `lifecycle.dev.start`, `lifecycle.stop`, `build.run`, `deploy.run`, `migrate.run`, `fork.run`, and state/health/log inspection. They do not depend on script paths or edit scripts directly.
3. **Shell scripts are an implementation lane.** Existing templates may expose lifecycle verbs through `.sh` files referenced by `manifest.json`. Creation Hosts may also implement lifecycle with Bun process management or another host-owned adapter, as long as the same semantic behavior is exposed.
4. **The current verb set is stable for v0 RC pressure:** `setup`, `dev`, `stop`, `build`, `deploy`, `migrate`, `fork`.
5. **Lifecycle environment variables are framework-owned.** The current stable envelope is:
   - `PNEUMA_WORKSPACE`
   - `PNEUMA_VERB`
   - `PNEUMA_MODE`
   - `PNEUMA_BUILD_DIR`
   - `PNEUMA_ARTIFACT_MANIFEST`
   - `PNEUMA_ENV_FILE`
   - `PNEUMA_PORT_HINT`
   - `PNEUMA_FORK_SOURCE`
   - `PNEUMA_FORK_TARGET`
   - `PNEUMA_MIGRATE_DIRECTION`
   - `PNEUMA_LOG_DIR`
   - `PNEUMA_SESSION_ID`
   - `PNEUMA_WS_URL`
   - `PNEUMA_INTERNAL_HTTP_TOKEN`
6. **Lifecycle markers are a script-lane protocol, not the agent API.** Scripts may emit:
   - `##pneuma:ready`
   - `##pneuma:stopping`
   - `##pneuma:service-ready <name> <url>`
   - `##pneuma:needs-confirm <label>`
   - `##pneuma:progress <pct> <label>`
   - `##pneuma:artifact <path>`
7. **Internal authority never comes from user-controlled HTTP identity.** `PNEUMA_INTERNAL_HTTP_TOKEN` is an internal channel token generated by the framework lifecycle owner and passed to the child runtime. It authorizes framework-internal runtime calls alongside the reserved `framework` principal. Public callers cannot become framework by setting headers.
8. **Build artifacts are host/profile outputs.** The lifecycle subsystem can require a manifest path and artifact directory, but concrete deploy targets such as Docker, local process, Vercel, registry push, or cloud rollout remain profile/host implementation choices.

---

## Consequences

### Positive

- Keeps ADR-0029 honest: Operation remains the app-creation primitive.
- Lets templates and Creation Hosts reuse process supervision, logs, markers, environment, and restart semantics.
- Gives backend agents a stable semantic surface without teaching them scripts or process details.
- Preserves the ability to replace shell scripts with Bun/Node/Python/local-cloud adapters without changing agent-facing contracts.

### Negative / Risks

- There are now two layers to explain: lifecycle semantic tools and script-lane markers. Docs must keep the distinction sharp.
- The marker grammar is intentionally small and may need versioning once external host authors depend on it.
- `PNEUMA_INTERNAL_HTTP_TOKEN` is suitable for local/in-process host-to-runtime authority. Hosted multi-tenant deployments may need signed service identity, mTLS, or another internal channel.
- Lifecycle still does not solve hot reload; schema/Operation/View/Policy changes may continue to require restart until a later milestone proves the reload boundary.

### Follow-ups

- M17 snapshot should record that lifecycle is pinned as a subsystem and no longer an open blocker for RC planning.
- M18 open-ended app pressure should check whether lifecycle verbs are sufficient for less schema-shaped applications.
- Future hosted deployment work should revisit internal channel authentication separately from local `PNEUMA_INTERNAL_HTTP_TOKEN`.
